# Historical File Reverse Application Scope

**Status:** Patch-export automated acceptance completed. Eligibility, isolated preparation and guarded single-file publication passed their broader backend checks. Historical-menu entry and confirmation/operation UI are implemented and focused race checks pass; a fresh complete make check is running. Native runtime acceptance and complete Sublime behavior parity remain unestablished. All mutating verification uses owned disposable repositories; no real-project Git mutation has occurred.

**Goal:** Let a person undo one historical text modification in their current worktree while preserving other files and later nonconflicting edits.

## Evidence and bounded decision

Local Sublime Merge Commit File resources declare revert_file separately from cherry_pick_file and create_patch. Their runtime commit range, index/worktree destination, automatic commit and conflict behavior remain unverified. Current SuperGit whole-commit revert cannot serve as a single-file implementation.

Fresh product review recommends “撤销此提交对该文件的修改…” with confirmation naming the complete path, source commit and first parent, current branch/HEAD, and the worktree-only result. This is a SuperGit implementation choice, not verified Sublime behavior.

Provisional main-thread ruling: require the source commit to be an ancestor of the captured current HEAD for the first implementation. This gives “undo this commit” an unambiguous relationship to the current branch and prevents reverse-applying an unrelated branch's patch merely because the text happens to match. Cost: this excludes deliberate cross-branch reverse application. It is a candidate task decision, not a durable product rule or human approval.

## First increment

- Only a normal single-parent source commit and one unchanged-path regular text file with an actual content modification.
- Reject root and merge commits, additions/deletions/renames, binary data, symlinks, gitlinks and file-mode transitions. Unsupported cases explain the reason.
- Require a clean index/worktree and no ongoing Git operation; ignored files retain normal Git clean-status semantics.
- Capture repository root/generation, source SHA/first parent/raw file metadata, current branch and HEAD. Revalidate before confirmation and again on acceptance and immediately before application.
- Reverse the selected commit's patch against the current worktree. Do not replace the whole file with its parent version: later nonconflicting edits must survive.
- Do not stage, create a commit, reset history or touch other files. An unapplicable patch fails without partial writes.
- Cancellation before applying produces no write. Once the single-file application has completed, report the actual result rather than claiming rollback from a late cancellation.
- Use only owned disposable Git fixtures in automated tests. No real-project mutation, commit, installation or publication is authorized by this document.

## Acceptance to implement later

1. A source commit modifies two files; a later commit edits a distant section of the selected file. Undo only the source change to that file. Compare exact selected/control bytes, HEAD, index and draft.
2. A conflicting later edit makes reversal unapplicable. Preserve all bytes, index and HEAD; show an actionable failure.
3. An unrelated-branch source, unsupported commit/file kind, dirty state or active Git operation cannot start a write.
4. Actual menu and confirmation cancellation perform no writes. Root/generation/source/branch/HEAD changes reject captured targets; refresh does not silently retarget them.
5. Literal Unicode/space/special-character paths and same basenames in different directories retain exact scope.
6. Backend validation and patch application run through the existing cancellable operation lifecycle. Review actual failure/cancellation boundaries before choosing subprocess commands.

## Read-only eligibility implementation

It checks the captured HEAD/branch, clean index/worktree, idle state, single source parent, source ancestry, literal exact changed-file membership, regular blob types and unchanged modes, NUL-free contents and Git numstat binary classification. ## Isolated result preparation

Added commit_file_undo_prepare.go and tests. PrepareCommitFileUndo validates eligibility, copies the current file through an os.Root boundary into an owned scratch tree, captures source identity/hash/mode, initializes an empty scratch Git repository with no user templates, streams the selected historical patch, and reverse-applies it only there. It rechecks the original target before returning a PreparedCommitFileUndo. Close removes only its owned scratch directory and is idempotent. There is no Apply/publish method yet.

Tests first failed for unavailable preparation, then passed under an isolated overlay. They compare the prepared result's exact content with later nonconflicting changes preserved, retain executable mode, verify source HEAD/index/worktree unchanged, and check cleanup after conflict/pre-cancellation and Close. Independent review identified a remaining evidence gap: cancellation after scratch creation is not yet exercised; do not claim the pre-cancel case covers that boundary.

An additional eligibility regression found that assume-unchanged/skip-worktree flags hide real edits from Status. Both actual fixtures initially returned an incorrect eligible result. The checker now compares the current path's filtered Git hash (hash-object without -w) with the current HEAD blob; hidden edits reject without changing index flags or contents. Combined candidate race passed 9.102 s; integrated eligibility/preparation race passed 8.849 s. Windows/Linux amd64 CGO-disabled backend test compilation passed.

Filesystem probes in an isolated Darwin overlay (build/_keyboard/undo_replacement_primitives_test.go, undo-replacement-overlay.json) passed under race 1.486 s. These establish primitives, not a complete guarded publishing operation or native-platform acceptance.

## Guarded publication increment

Added ApplyPreparedCommitFileUndo(ctx, prepared) in commit_file_undo_publish.go. It serializes app writes and the prepared-result lifecycle, repeats eligibility, checks original identity/mode/SHA256, copies the prepared result to an exclusively created random adjacent file, preserves permissions through its handle, syncs/closes successfully, rechecks eligibility while excluding only that exact untracked owned temp, verifies the anchored parent and original again, and checks cancellation before rename. Successful replacement consumes the preparation and reports success without reclassifying a late cancellation as rollback. Failure cleanup uses the anchored parent handle and reports cleanup errors. UI remains disconnected.

Important limit: external programs do not share writeMu. Final validation followed by rename is not an atomic compare-and-swap against another process. The candidate checks detect edits observed before replacement; they cannot promise to reject every external write in the final check/rename interval. Do not advertise absolute concurrent-editor protection. Native Windows/Linux replacement semantics and arbitrary I/O-failure acceptance remain unverified.

Product review retained the bounded scope and requested stale confirmations reject. Design retained scrollable full targets, fixed footer, initial Cancel focus, Escape cancellation and focused-action Enter behavior; those UI requirements are not yet implemented.
