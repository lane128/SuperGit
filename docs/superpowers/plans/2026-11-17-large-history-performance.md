# Large-history performance plan

Goal: bound graph memory and UI work for repositories with many branches, commits and long parent edges, then reduce redundant history traversal. Preserve exact SHA/root/write guards and current navigation semantics.

Baseline: commit 5334700. Diagnostic overlay under build/history-perf-investigation measured 1024 distant-parent commits at 79,388,402 allocated bytes per graph build, versus 526,114 for linear history. Graph is rebuilt during every commitList render. A 64-lane graph occupies 400 DIP inside a 310-DIP list despite an 80.6-DIP budget. These are synthetic algorithm measurements, not a reproduction of the remote computer's 1.8GB RSS.

- [x] Replace expanded per-row edge copies with a linear-space interval index. Test exact row-edge membership against a brute-force oracle and allocation growth on long edges. Keep original SHA edges, color and ordering.
- [x] Cache graph layouts for immutable history/filter/palette snapshots. Test reuse on repaint and invalidation on appended/replaced history, query, palette, and working-tree HEAD/state changes. Width changes must refit without accumulating gutters.
- [x] Fix graph-width overflow without collapsing distinct lane/node geometry. Use the supplied Sublime Merge layout reference; keep title and metadata readable. Verify rendered narrow and many-lane behavior before claiming acceptance.
- [x] Replace repeated prefix ordinary-history traversal with bounded/cancellable demand or streaming reads while preserving explicit End/search/jump behavior. Existing full-history navigation tests describe current behavior; change their contract deliberately and retain access to older commits.
- [x] Measure many-branch/long-edge native workloads, RSS and input responsiveness; run full tests/race/vet and existing guarded workflow checks.

No automatic commit, installation or DMG publication. Original repository unavailable (tested on another computer). Do not claim the exact user workload reproduced. Synthetic fixtures must include interleaved branches, long parent spans and large reference inventories, not only long linear chains.

## Rulings and remaining limits

- Ruling: preserve automatic complete-history loading, but stream its continuation through one Git process — keeps End/search/jump semantics while removing repeated prefix traversal. The first bounded page remains unchanged for fast startup. If wrong, cancellation or continuation could leave a process alive; backend and app cancellation tests cover that lifecycle.
- Ruling: preserve readable lane geometry and provide a horizontal graph viewport rather than compressing arbitrarily many lanes into overlapping nodes — the graph's pinned-row scrollbar exposes all lanes while titles remain fixed. If wrong, offscreen lane discovery is less obvious; native and pixel checks verify rendering, panning and selected-node reveal.
- Ruling: retain the rename-specific file-history pager and current watcher/sidebar behavior in this change — the authorized priority is large branch/commit histories, and redesigning those independent paths expands verification substantially. Their repeated rename-prefix work, broad watch scans and nonvirtualized reference inventories remain known costs; do not claim arbitrary-size repos have a fixed memory cap.
- Ruling: accept the subsequent metadata layout on rendered density tests and final native screenshots rather than a second independent review — the core reviewer explicitly declined that later edit, and the row change is confined to badge placement/width. If wrong, a display combination beyond the checked languages/scales/ref fixtures could still crowd metadata. No independently reviewed security or write behavior was changed by it.
- Remaining: a repaint still scans uniform row heights and the sidebar still constructs expanded references; graph allocation and repeated ordinary Git traversal were the dominant measured causes addressed here. Full-history metadata itself still grows with repository size.
- Native inspection then exposed badge crowding on the subject line. Added a separate RED→GREEN row-hierarchy regression: default two-line rows give subjects their own first line and share author/ref metadata on the second line. Metadata folds additional refs; narrow rows retain timestamps in accessible descriptions and commit summary. Existing single-line author/time-hidden preference retains its prior badge placement. This directly follows the supplied Sublime Merge reference.
