# SuperGit 单需求自动发布工作流

**Status:** Approved — 2026-11-28

## 用户如何发起任务

提供一个明确的「授权自动交付」入口，可以是本地命令，也可以是聊天中的显式指令。例如「自动交付：仓库标签的关闭按钮支持键盘聚焦；沿用现有样式」。该入口展示或引用固定的授权范围，一次提交就覆盖需求分析、范围内的设计决策、实现、测试、审查、提交、推送、PR、合并到 main、创建新 tag 和发布 GitHub Release。普通讨论或只读请求沿用原来的工作方式。

协调器在任务开始时保存授权人、原始请求、仓库、目标分支、分发渠道、版本策略、验收要求和策略版本。默认目标为本项目 main、现有 macOS Apple Silicon 渠道，版本为交付时下一个 patch。用户可以在请求中指定 minor 或具体版本。需要改变兼容性承诺、发布渠道或需求范围时暂停，列出差异。确认后形成有记录的授权修订。授权只用于这条需求，可以在进入下一项外部操作前撤销。删除已发布版本、移动已有标签、强推或覆盖他人工作需要单独授权。

## 运行方式

推荐以持久化协调器记录状态，GitHub PR 保存差异和检查结果，macOS 执行器负责原生验收，受保护的发布任务负责签名和上传。沿用现有 Go、Make、MyGo 脚本和 GitHub Releases。纯对话技能改造最少，但会话中断后难以核对发布副作用。全云部署便于集中运维，前期还要准备可驱动 GUI 的 macOS 环境和签名环境。首期协调器可在本机运行，重启能继续，宿主离线期间任务排队。

每条任务分配唯一 ID，使用独立 worktree。持久记录阶段、重试次数、授权、基线与候选提交或内容指纹、检查所针对的内容、PR、版本、tag、归档哈希和发布结果。每次外部操作先持久记录意图，执行后重新读取真实状态，再记成功。保留事件历史，让用户随时看到当前阶段、已通过项、阻塞原因和发布链接。

## 从需求到版本

| 阶段 | 执行与通过条件 |
| --- | --- |
| 需求分析 | 将原始请求变为范围、非目标、验收场景和 T1/T2/T3 等级。检查已有行为与重复任务。用户可感知且无法由现有产品规则推断的歧义才提问。需求已在现有版本满足时给出证据并结束，避免空版本。 |
| UI 设计与设计审查 | 按界面影响选择，纯后端记录跳过理由。局部改动沿用现有组件，重大变化生成原型。独立审查者按需求、键盘交互、明暗主题、窗口尺寸和失败状态验收设计。满足既定标准即进入实现。出现范围外选择时返回需求阶段。 |
| 实现与单元测试 | 在任务 worktree 实现。缺陷先复现，新行为有断言，按影响面跑定向测试、全量检查、race 或 SDK 检查。项目包范围统一为 `./cmd/... ./internal/... ./tools/...`，显式保留 MyGo SDK 检查。文档类任务校验相关引用或命令。 |
| 代码审查 | 提供相对基线的完整变更，覆盖已暂存、未暂存和新增文件。T1/T2 可用现有轻量检查，T3 由独立审查者只读审查。阻塞问题回实现阶段，复核变更并重跑受影响检查，最多三轮，未解决时说明原因并暂停。 |
| 原生验收 | 用户可见变更用 `make app` 构建并实际启动，用隔离的仓库和配置驱动原生场景。记录标准包与 e2e 包分别跑了什么。UI 对照批准的设计，Git 写操作核对 refs、HEAD、Index、工作文件。已规定须本人检查的关键流程，在授权时列出人工验收项；验收结论可单独提供，提交、合并与发布继续使用原授权。无法验证的必需场景阻塞交付。 |
| 提交、推送与 PR | 核对候选内容与通过审查及验收的内容一致，按原授权提交英文 commit、推送任务分支、开 PR，关联需求、验收证据和回退方式。远端必需检查必须针对当前候选。 |
| 合入 main | 所有自动任务共享一个从合并持续到发布核验完成的队列。取得队列后刷新远端，用当前 main 与 PR 生成集成候选，验证组合结果。若基线变化，重新验证；实质冲突回实现和审查。通过后合入，核对实际 main 的代码树与验证的集成内容一致。 |
| 签名与发布 | 从干净且刚与 origin/main 核对一致的 main 构建。在独占队列内确定版本，在预检分支、目标提交和密钥配置后创建本次 tag。校验 tag 指向当前 HEAD，再打包。校验版本、公钥与签名私钥的对应关系、归档哈希、Ed25519 签名、包标识及 codesign。暂存待发布资产，核验后公开 Release，回下载公开资产核对哈希及清单。记录发布链接，再放行下一条。 |

## 失败、恢复与授权隔离

- 判断重试以真实状态为准。已推的同一提交、已合的同一 PR、指向同一 SHA 的目标 tag 和同一发布记录可以沿用。重启后从远端与本地持久记录重建进度。遇到同名但内容不同的 tag、Release 或资产，保留现场并暂停。
- 从合并到发布的队列须覆盖所有自动交付入口，并配合 main 保护规则限制旁路写入。前一需求已合并但尚未发布时，后续任务可继续分析、编码和检查，合入 main 等待。发布窗口内发现外部推进时冻结队列，保留已验证的版本归属，交由维护者处理。
- 为每个候选版本保存已验归档、清单和校验和。上传超时或重复通知时先查询 Release 状态，复用相同字节并补齐缺项。发布后回下载失败时优先重试核验；发现内容不一致则告警并保留证据。修复已公开版本采用新需求、新版本。
- 签名私钥与发布凭据由维护者控制的执行环境持有。功能分支的测试和审查任务只拿到完成本阶段所需的权限。验包工具和发布授权策略使用受信任版本；会修改它们或签名机制的需求进入现有关键流程人工检查。首次配置凭据、分支保护和服务权限由维护者完成。
- 统一 `CLAUDE.md`、`feature-flow` 和实际执行入口。显式自动交付模式允许独立设计审查和原生验收按标准自动推进，人工验收项按上表处理。普通模式保留现有审批。创建标签与 Release 的显式确认来自本条需求的授权记录。运行时校验具体动作和目标，避免依赖 Markdown 约定或全量放行 Git 命令。

## 首期执行边界

首期建议限定为维护者单用户模式。部署时绑定维护者的受信本地入口或已认证账号标识，授权、修订和撤销均由该身份直接发起。Issue 正文、评论转述和 Agent 生成的内容只作需求材料。

合并前以最近一次已验证的公开版本为基线，核对 main 到候选版本的差异归属。允许由受信路径清单界定的发布记录等纯文档提交，其他未授权交付的产品变更阻塞入队。如果授权在合并后撤销，保留分支、标签和发布记录，冻结后续合并。维护者可修订授权继续本任务，或另行授权通过普通 revert 提交恢复基线。核实 main 的产品内容和待发布版本归属后解锁队列。已公开的发布可继续只读核验；撤销授权不会自动删除公开资产。

构建进程只取得公开更新公钥，在无签名私钥和发布令牌的执行环境运行候选代码。构建完成后将产物交给独立的受保护执行器；该执行器仅运行事先固定的打包、校验与上传程序，不执行候选仓库提供的 Makefile、脚本或二进制。修改发布工具先用临时凭据验证，再由维护者显式启用新版本。

## 落地与验收

1. 先统一验证命令、修复 release-pack 预检，将独立验包检查做成项目固定入口，编写失败用例。同步两套项目规则并明确自动与普通模式。
2. 实现任务状态、授权记录、独立 worktree、审查与 macOS 执行器。在本地裸远端和临时签名环境完成一条 UI 需求和一条纯后端需求，验证通过路径及跳过理由。
3. 在隔离发布目标验证两条任务同时就绪、main 推进、审查失败、漏公钥、创建 tag 后崩溃、上传超时、已发布但回下载中断。要求同一需求只产生一个版本，恢复后归档哈希一致，失败的必需检查阻止发布。
4. 维护者配置受保护的发布环境后，用一条明确授权的小需求试运行到真实发布。完成条件为可从需求记录追踪到用户可下载的版本，公开资产与已验资产一致，自动化没有在成功路径上重复请求批准。
