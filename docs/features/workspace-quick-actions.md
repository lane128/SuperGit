# 工作区一键 Stash 与清理

Status: Approved — 2026-11-27 用户指示按预览实现、自测、合并 main 并发布 1.0.1；采用建议方案 A。
Date: 2026-11-26
Related: 基于 `da155a8`；T3（新功能、Git 写操作与删除）

## Background and goal

在工作区提供两个针对整个当前仓库的快捷入口，方便用户保存当前工作或主动丢弃改动。

- **一键 Stash**：保存已暂存、未暂存及未跟踪文件，成功后工作区无待提交改动；保留被 Git 忽略的未跟踪文件，可以通过已有 Stash 功能恢复。
- **一键清理**：先预览并确认，将当前提交中已有文件恢复到该提交，同时撤销暂存。可勾选「同时删除新增文件和目录」，默认不勾选。勾选后，在支持的仓库状态下，Git status 干净。
- 两者保持当前分支、HEAD 和分支提交历史不变。Stash 操作按其用途新增 refs/stash 记录。
- 清理明确提示丢弃的修改及删除的新增文件无法通过本操作撤销；用户应先 Stash 再保留恢复能力。

### 已批准的设计语义

1. “新增”按当前 HEAD 是否存在该路径判断：默认也保留已暂存的新文件，只撤销它们的暂存。重命名恢复旧路径，新的目标路径默认保留；勾选删除时才删除该新增目标。
2. 无首次提交、冲突、进行中的合并/rebase/cherry-pick/revert/am，以及不能安全清理的子模块/嵌套仓库状态，拒绝执行并解释原因，不自动中止或递归处理其他仓库。
3. 两个入口作用于整个工作区，不受当前选择、筛选或文件分组影响；不新增设置项和快捷键。

## Non-goals

- 不重做工作区布局，不新增独立页面，不改变已有逐文件放弃、暂存、Stash 命名/恢复或命令面板入口的语义。
- 不新增自动备份、回收站、撤销清理、Stash 命名表单或恢复向导。
- 不清理忽略文件，不递归清理子模块或嵌套仓库，不移动分支或重写提交。
- 不支持在外部程序持续写入仓库时提供跨进程原子事务；检测变化、缩小竞争窗口并如实报告部分完成。

## Approach

### 交互

按用户反馈，两个低频操作放在 `view.go:workbenchToolbar` 顶部命令/分支控件右侧，文件区只保留现有暂存全部、撤销暂存和放弃未暂存改动。快捷入口采用 24×24 图标按钮与 tooltip：Stash 用归档图标，清理用橡皮图标；名称、整个工作区的作用范围及是否立即执行写清楚。所有文案提供简体中文和英文。

预览并列展示三种方案；2026-11-27 用户指示按预览实现，采用建议方案 A，其余方案仅作对照：

- **A（建议）· 合并为拆分按钮**：主图标立即 Stash 全部（含未跟踪），相邻箭头保留现有“仅已跟踪 / 含未跟踪”的命名流程；清理在旁边，移除右上重复 Stash 菜单。菜单支持键盘导航、Esc 和点外部关闭。
- **B · 保留原菜单**：分支旁放两个独立快捷按钮，右上原 Stash 菜单保留。保持既有位置，但出现两个 Stash 入口。
- **C · 仅保留快捷按钮（仅供对照，不建议）**：分支旁放两个独立快捷按钮，移除右上 Stash 菜单。已有命令面板只提供带命名的“仅已跟踪”流程，原“含未跟踪并填写说明”的全工作区入口会丢失，与保留既有能力的目标冲突；若选 C，需先明确该取舍，不能假定命令面板覆盖原菜单全部能力。

实施采用主界面示意中的 A。最小 900×640 窗口中保持快捷入口可点，优先截断长分支标签，不能遮挡分支选择器或同步控件。

可直接打开的设计预览：`design/workspace-quick-actions.html`（本地、被 `.gitignore` 忽略，不参与提交）。支持浅/深色与中/英文切换；默认展示未勾选删除的状态。可用 `?theme=dark&lang=en&delete=1` 固定深色、英文和勾选删除后的对照状态。加 `&menu=1` 展示 Stash 菜单展开。静态对照：`design/workspace-quick-actions-light.png`、`design/workspace-quick-actions-dark-delete.png`；三方案局部对比图：`design/workspace-quick-actions-options-light.png`、`design/workspace-quick-actions-options-dark.png`。

通用确认框当前只适合短消息（五行限制），无法承载完整影响列表和复选框。因此新增局部 `workspaceCleanState` 与专用清理对话框（预览宽 520px，复用现有卡片、危险按钮与复选框样式），复用 `workbenchModal` 和 `choice.Checkbox`，不扩展为通用表单框架。将状态接入 `dialog_scope.go` 的 pending-dialog 守卫、Esc/关闭路由、仓库切换和刷新生命周期。

- **Stash**：点击立即开始，固定包含未跟踪文件，不额外询问名称；使用包含时间和短唯一标识的自动说明，例如 `SuperGit workspace 2026-11-26 14:30:00 [a1b2c3d4]`。成功提示已保存到 Stash，刷新文件区与 Stash 列表。
- **清理**：异步读取真实状态并准备预览，预览完成后才允许确认。勾选项每次打开重置为 false，选项变化重新计算预览，加载期间禁用确认。
- 路径列表完整可访问、可滚动；计数不重复统计同一路径，不以截断摘要代替完整影响范围。明确区分恢复、撤销暂存、删除、保留，重命名展示两端。
- 清理按钮采用现有危险操作样式，默认焦点落在取消；Esc 取消；处理期间防重复提交。不开启未请求的全局快捷键。
- 无仓库、忙碌或确实无可处理内容时禁用入口。只有未跟踪新增文件且无任何索引变化时，仍能打开清理，但默认无改动可执行，勾选删除后方可确认。若新增文件已暂存或标记 intent-to-add，默认模式仍可确认撤销暂存并保留文件。
- 对不能从 UI 快照确定的阻断条件，后端预检给出具体原因。错误及取消后重新刷新，不把可能部分完成的操作显示为成功。
- 切换仓库、关闭确认框或更换选项时，失效的异步结果不得更新新界面，也不得执行旧确认。

### Stash 后端

- 复用 `Repository.SaveStash(ctx, message, true)` 的 `stash push --include-untracked` 能力；不得使用 `--all`。
- 为快捷入口补充同一写锁内的必要预检与结果校验；如需包装，抽出私有锁内 helper，避免持锁调用现有加锁方法造成死锁。
- 检查存在 HEAD、无进行中操作、无冲突、无不支持的子模块或未跟踪嵌套仓库。稀疏检出及隐藏改动的特殊索引标记先明确拒绝，防止误报已清空。
- 沿用现有对子模块内部修改的保护；子模块 gitlink 变更或无法确认父仓库 Stash 能完整恢复的状态也拒绝。
- Stash 同样进行忽略路径碰撞预检：例如 HEAD 中已有 `p`，索引暂存删除 `p` 后，工作区出现同名被忽略替代文件，Git 的 Stash 清空步骤可能覆盖该替代物。此类路径/祖先碰撞必须在调用 Git 前拒绝，保持忽略文件、索引、HEAD 不变；不能仅依赖 `--include-untracked` 保证忽略文件安全。记录原有忽略集合并检查恢复 HEAD 的忽略规则是否会让其出现在 status 中，无法满足保留及清空要求时也预先拒绝。
- 完成后复读状态与 Stash 引用，只有实际新增记录且待处理改动已清空才提示成功。linked worktree 共用 Stash 栈，不能只把最新 `refs/stash` 当成本次结果；采用每次操作的唯一自动说明标记，在新增记录中识别并记录本次 Stash OID；说明在已有 Stash 列表正常显示，不额外改造列表或要求用户输入。
- 失败后仍刷新 Stash 与工作区：Git 可能已创建 Stash，但工作区清理未完成，此时保留记录并明确提示，不自动重试或弹出；若无法确认本次记录或外部操作干扰结果，提示结果需检查，不把其他 worktree 的 Stash 当作本次成功。

### 清理后端：准备与执行

新增工作区级 `PrepareWorkspaceClean` / `CleanWorkspaceChecked`（名称可按实现调整），不直接改变现有逐文件放弃 API。

**准备阶段（只读）：**

1. 获取仓库写锁，验证仓库状态和支持边界；绑定规范仓库根目录、当前分支、HEAD、操作状态、选项和完整索引。
2. 从 HEAD 树、索引及工作区状态推导精确操作集合：恢复 HEAD 已有路径、撤销暂存、保留/删除 HEAD 中不存在的新增路径。处理暂存删除后同名新文件、重命名、文件/目录类型变化和 intent-to-add，不能只看 `status` 的 A/M/D 字母。
3. 用 Git 的忽略规则和现有 clean 预览逻辑识别删除候选，包括非忽略的空目录。保护准备时被忽略的未跟踪路径；若恢复 `.gitignore` 后有路径变为被忽略，也保留。不得恢复后重新全量 clean 而扩大删除范围。
4. 对需要覆盖/删除的路径记录文件内容摘要、模式、符号链接目标和父目录身份；索引记录、HEAD/分支、忽略规则变化和文件缺失也进入校验范围。复用现有 `PreparedDiscard`/`CleanPreview` 的成熟机制，不调用它们不匹配的执行语义。
5. 若恢复 HEAD 的文件必须覆盖保留的未跟踪/忽略路径，或路径祖先被符号链接替换，拒绝并展示阻断路径，不为达成干净状态牺牲保留约定。
6. 若忽略规则变化导致“保留原先忽略文件”与“勾选后 status 干净”冲突，预检拒绝并解释；支持边界内才允许进入确认。

**执行阶段：**

1. 同一写锁内重做预检并与准备快照比较。路径内容、索引、分支（即使指向相同 SHA）、HEAD、忽略规则、目录身份或选项变化，拒绝旧确认；提示重新打开预览。写操作前完成全部目标验证。
2. 先根据 HEAD 与实际文件类型建立路径依赖顺序。若 HEAD 的文件 `p` 已被目录 `p/new` 替换，默认保留新增时在任何写入前拒绝；勾选删除时，只有 `p/new` 及阻挡目录全部在批准删除集合、没有受保护内容，才先以受检机制删除阻挡路径，再恢复 `p`。HEAD 目录被新增文件替换时同理；不能让 Git 隐式删除未批准的阻挡物。不能完整证明顺序安全的类型变化在写前拒绝。
3. 按批准的顺序处理阻挡路径后，撤销暂存并恢复 HEAD 已有路径；新增路径默认仅撤销暂存并保留工作文件。通过 Git 的 index/restore 能力工作，不使用会移动分支的命令或无范围的 `reset --hard`。具体命令序列以针对真实 Git 的回归测试为准。
4. 勾选删除时，删除其他预先批准且再次校验的新增文件和目录。所有删除（包括恢复前的阻挡物）都复用基于 `os.Root`、父目录身份检查、逐文件删除和由深到浅移除空目录的机制；不递归删除整棵目录，不使用 `clean -x/-X/-ff`。
5. 清理不递归更新子模块；不改变工作树之外的文件。不覆盖/删除清理前后应保留的忽略路径。
6. 执行后复读 status、HEAD 和分支。勾选删除的成功结果必须无待提交改动；默认模式允许保留新增文件，但索引与 HEAD 相同，已有文件恢复至 HEAD。
7. 操作并非全有或全无：恢复、删除或取消中途失败时，返回阶段及失败路径，刷新实际状态，提示可能部分完成。不自动回滚覆盖用户的新写入，不自动重新执行破坏操作。

### 支持边界

- 支持普通仓库、正常 linked worktree 和 detached HEAD；保持分支身份/HEAD 不变。
- 没有首次提交：两个快捷操作拒绝，解释没有可保存/恢复的当前提交；不自动创建提交。
- 有冲突或集成操作未完成：拒绝，不删除操作元数据或帮助用户中止。
- 子模块无变化时保留；子模块内部改动或 gitlink 变更拒绝。未跟踪嵌套 Git 仓库在需要清空的范围内时拒绝，不递归处理。
- 稀疏检出、`skip-worktree` / `assume-unchanged` 等可隐藏实际改动的索引状态，首次实现拒绝并解释；不擅自修改索引标记。
- 特殊设备文件、不可读路径、扫描输出截断或无法证明删除范围安全时拒绝；不对未知范围继续执行。
- 符号链接按链接本身处理，不跟随到仓库外或其他目录。大文件摘要采用流式读取，准备阶段可取消。

## Alternatives and trade-offs

- **采用：工作区级预览/校验执行，复用现有 Stash 与路径安全逻辑。** 能把恢复、撤销暂存和可选删除纳入同一次确认，保留现有入口语义。需要新增聚合操作与测试。
- **串接现有“放弃文件”和“清理未跟踪文件”。** 现有放弃只恢复工作文件到 index，不能正确恢复 HEAD；两个独立快照/锁也无法保证确认覆盖整组操作，故不采用。
- **硬重置后直接 clean。** 命令少，但可能删除默认应保留的已暂存新增文件、覆盖未跟踪阻挡路径，并在 `.gitignore` 恢复后扩大删除范围，故不采用。

上述实现选择为开发方建议，产品语义及边界由本设计审批确认。

## Test plan

### Unit / integration tests（先红后绿）

- Stash 混合已暂存/未暂存/未跟踪，包括同一路径 staged+unstaged、只有新增、二进制、中文/空格/换行/前导短横线路径。确认记录新增、status 干净、忽略文件字节不变，并通过已有 `ApplyStash --index` 恢复数据及暂存状态。
- Stash 忽略路径碰撞：HEAD 有 `p`，暂存删除后创建同名被忽略替代物；执行前拒绝，逐字节比较忽略替代物、索引和 HEAD 不变。另测 HEAD 文件被含忽略内容的目录替代、忽略规则恢复后原忽略文件暴露，以及 linked worktree 并发新增其他 Stash 时本次 OID 识别。
- 默认清理：混合改动、暂存删除、未暂存删除、已暂存新增、部分暂存新增、intent-to-add、重命名和复制；索引回到 HEAD，已有文件恢复，新路径保留，分支/HEAD/历史不变。另测“只有已暂存新增”和“只有 intent-to-add”：默认确认可用，执行后内容保留且暂存撤销；只有未跟踪新增时默认确认不可用。
- 可选删除：上述集合加多级目录、空目录、忽略与非忽略文件混合目录、符号链接；status 干净，忽略文件与外部目标逐字节保留。
- 忽略规则：修改/删除/新增 `.gitignore`，嵌套忽略文件、`.git/info/exclude` 和全局 excludes；不因恢复忽略规则扩大删除。保留与干净结果不能同时满足时无写入拒绝。
- 类型与重叠：文件换目录/目录换文件、重命名两端、暂存删除+同名未跟踪记录。明确 fixture：HEAD 中 `p` 是文件，工作区删除 `p` 后创建 `p/new`；默认清理无写入拒绝，勾选删除时受检删除 `p/new` 和空目录后恢复 HEAD 的 `p`；若目录还含忽略文件，则两种模式均在写前拒绝。补对称目录换文件用例及顺序中途失败后的准确状态。
- 预览后修改内容（status 字母不变）、暂存变化、切分支到同 SHA、HEAD 变化、忽略规则变化、新增文件进入待删目录、父目录改名/换符号链接、目标被换 inode：拒绝旧快照且不删除未批准内容。
- 支持边界：unborn、冲突、各类进行中操作、脏子模块/gitlink、嵌套仓库、稀疏检出/特殊索引标记；拒绝前后比较 HEAD、索引和工作文件，确认无副作用。
- 注入恢复/删除失败与取消，断言错误不会伪装成功，刷新后状态准确，Stash 部分成功时保存记录仍可见。
- UI：顶部分支旁两个入口范围不随选择变化；按选定方案测试 Stash 主图标立即执行、菜单命名流程及键盘焦点；默认 checkbox=false，重新打开不记忆；切换选项预览失效；错误/空/加载/忙碌/取消；仓库切换与迟到回调；中英文文案；操作后工作区与 Stash 列表刷新。

### 可复现 fixture 与自动化入口（实施阶段交付）

新增脚本的约定入口为：

```sh
python3 -I scripts/native-lobe-workspace-quick-actions.py --app "$PWD/build/SuperGit.app" --scenario all --output docs/acceptance/2026-11-26/workspace-quick-actions
```

脚本仅对自己创建的新临时目录初始化 fixture，每个场景使用独立仓库，不接受一个现有仓库后重置/清理它。初始化一个提交，包含 `.gitignore`（忽略 `ignored/` 与 `*.keep`）、`staged.txt`、`unstaged.txt`、`mixed.txt`、`deleted.txt`、`rename-old.txt`。随后生成：

- `staged.txt` 修改并暂存；`unstaged.txt` 仅修改；`mixed.txt` 暂存一次后继续修改。
- `added-staged.txt` 新增并暂存，`new/deep/file.txt` 与空目录 `empty/` 不暂存。
- 删除 `deleted.txt` 并暂存，将 `rename-old.txt` 改名为 `rename-new.txt` 并暂存。
- 写入 `ignored/keep.txt`、`new/preserve.keep`，并在另一个任务临时目录建立符号链接外部目标。

脚本在每个场景记录 `status --porcelain=v2 -z`、HEAD、符号分支名、`ls-files --stage -z`、已有 Stash OID 集合，以及所有文件类型/内容 SHA-256 和符号链接目标。取消场景全量指纹相同；Stash 恢复场景比较原索引及内容；默认清理比较 HEAD 树与原新增文件内容；勾选删除要求空 status、索引等于 HEAD 且受保护文件/外部目标摘要不变。额外场景分别构造过期确认、忽略路径碰撞、文件/目录替换、子模块和嵌套仓库。操作完成后等待控件恢复 enabled 和状态刷新，不能只等待成功提示。

实施结果：原生脚本覆盖六项主流程，每次运行共享一个自建临时仓库，先 Stash/Apply 还原，再验证取消、默认清理、勾选删除与过期确认。文件/目录替换、空目录、忽略路径碰撞、子模块和嵌套仓库等边界由真实 Git 回归测试覆盖。2026-11-27 三组原生运行共 18 项通过；实际命令、范围、限制及发布验证见 `docs/acceptance/2026-11-27/README.md`，以该记录为准。

## Risks and rollback

- 清理不可撤销。默认不删新增，明确展示范围和警告；测试使用任务创建的独立 fixture。用户需要恢复能力时先 Stash。
- 外部编辑器/Git 不受进程内写锁约束，无法保证绝对原子性；写前验证、逐路径身份检查、明确部分完成和结果复查降低影响，不能宣称事务保证。
- 大仓库快照成本：后台流式读取、可取消、禁止重复提交；不缓存未经重新校验的批准结果。
- 回滚代码：提交后用反向提交撤销本功能，不重置用户分支历史；提交说明包含验证与回滚方法。
- 回滚代码不能恢复已被用户确认清理的数据。Stash 操作产生的记录不随代码回滚删除。
- Phase 1 设计审批前不写产品代码；Phase 2 审查/验证通过后进行 Phase 3；用户通过真实应用验收后再按授权提交和推送，不自动发布、打 tag 或执行破坏性 Git 命令。
